Summary

One app now serves two kinds of people. A phone number that owns a café opens the owner dashboard; every other number opens the original JOLO customer interface. Over iMessage, a first-time texter is asked whether they're an owner or a user, and owners are signed up with their café on the spot. A trends job scrapes café blogs (and Reddit, where reachable), joins what it finds with live menus and customer activity, and feeds an analytics hub for owners and drink suggestions for customers.

How it fits together

Scraping is slow and never runs on the phone. A Python job writes finished results to Firestore, and the app only reads them. The bridge talks to the agent for menus and writes the café record when an owner signs up.

Highlighted boxes are this part of the project; dashed boxes belong to teammates or live outside the repo. On a phone, scroll the diagram sideways.

Two interfaces in one app

At sign-in the app looks for a café whose ownerPhone is the verified phone number. Found: the owner dashboard (Menu, History, Insights, Account). Not found: the original JOLO interface (Finder, Social, Favorites, Profile), ported from the original JOLO app with its map, location and café data. Each side is unreachable from the other, even by deep link.

iMessage: owner and user flows

The first text from a new number opens one question. Owners give their details in one message and their café is written at once; users are welcomed and pointed at the app. Tested from a real phone through the bridge:

Whats on the menu at barbara'sBarbara's: Espresso $3.00, Cortado $4.50, Latte 12 oz $3.50 / 16 oz $4.25… (updated 3 days ago)

Every reply arrived within about two seconds. Ownership is decided only by the phone number iMessage reports, never by message text. Later texts go to the agent with the person's role.

The data scraper: owner insights and customer suggestions

The scraper in ~/Scraper_test has two parts, and the trends job uses both: blog-finder (DuckDuckGo search, blog feeds, trend phrases) and the social scraper (Reddit through a local camofox browser; TikTok through ScrapFly). Only titles and links are kept; page text, usernames and media are dropped.

Live blog data first produced names like "Espresso machine" and "Latte comes". The job now keeps only names that end in a drink, contain no headline words, and are more than a menu staple, so trends read like things you'd order: cold brew, matcha, oat milk shaken espresso.

What's left

Belongs to other parts of the project

  • Menus from photos: the agent and the menu reader. Until then owners add menus in the app, and the stub agent only knows a demo café.
  • Weekly customer-ask insights: written by the agent's backend, so "Customer asks" stays empty for real cafés until that exists.
  • iMessage questions as asks: the agent would log them as events in the same shape.

How to run it

Full setup is in docs/trends-and-insights.md. With the emulators running:

# demo data (emulator only)
cd jolo-app
FIRESTORE_EMULATOR_HOST=127.0.0.1:18180 npm run seed:cafes
FIRESTORE_EMULATOR_HOST=127.0.0.1:18180 OWNER_CAFE_ID=owner-<digits> npm run seed:trends-demo

# trends, once, from the repo root
FIRESTORE_EMULATOR_HOST=127.0.0.1:18180 .venv/bin/python -m recommend.job --analytics --scrape

# trends, daily, against the real project
docker build -f recommend/Dockerfile -t jolo-trends .
docker run -d --restart unless-stopped -v ~/Scraper_test:/scrapers:ro \
  -v /path/to/key.json:/secrets/key.json:ro -e JOLO_SERVICE_ACCOUNT=/secrets/key.json jolo-trends

# every automated suite
bash scripts/test_all.sh
